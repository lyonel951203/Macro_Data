## 一、背景与问题定义

### 1.1 起点

用户维护 `E:\Macro_Data` 宏观 PIT（point-in-time）数据库项目：

- **主库** `macro_pit_v2.duckdb`：append-only 证据层，每格记录含来源、PIT 等级（A/B/C/D）、发布时间、原文件 SHA-256；

## 二、可行性论证的三个关键结论

### 2.1 Wind 能补什么、不能补什么

| 缺口类型 | 例子 | 结论 |
|---|---|---|
| 序列起点太晚 | PMI 从 2009-07 才有（Wind 有 2005-01 起）；M2 从 2007-06（Wind 1996 起） | ✅ 可大幅向前延伸 |
| 中段空洞 | 2005-2008 财政/货币/投资类大面积空白 | ✅ 可按数据期回填 |
| 结构性空缺 | 失业率 2018 前、社融存量月度 2015 前、综合 PMI 2017 前 | ❌ 官方未发布，Wind 也没有 |

### 2.2 PIT 语义分层

PIT 判定是两步：**① 该数据期在截点时是否已发布（可见性）→ ② 已发布则取当时最新版本（版本）**。

- 发布日历/发布规律解决第①步；
- Wind 连接器（`natural_language_get_edb_data`）**只返回终值序列 + 指标级单一 updateDate**，拿不到逐点版本历史（实测验证）——第②步对不修订字段（CPI/PMI/M2 等，初值≈终值）无损，对修订敏感字段（GDP/社融/财政）有偏差；
- 发布滞后有极强规律性（见 3.1 的实证分布），可用"数据期末 + 经验滞后"重建可见性。

### 2.3 估计发布日的四个边界（用户认可的设计约束）

1. 估计日期进独立字段 `estimated_available_at`，**绝不填 `release_at`，绝不升等级**；
2. 经验日期必须用已验证样本（库内 A/B 真实发布日）校准，不拍脑袋；
3. 最大残留风险是**终值≠当时版本**（GDP 2021Q3 原值 4.9% vs 修订后 5.5%）——视图定性为"终值+估计可见日"；
4. 必须配滞后敏感性测试（+7/+15 天/+1 月）才能用于下游结论。

## 三、PIT_work 视图的设计与实现

### 3.1 第 1 步：实证滞后分布（`scripts/tools/calibrate_release_lag.py`）

只读主库，对 47 个序列的 5,508 个"数据期首次发布"样本（A/B 记录）统计发布滞后：

| 指标组 | 滞后中位 | P10–P90 | 规则 |
|---|---|---|---|
| PMI 全系列 | 0 天（当月末） | 0–1 | 月末最后一天发布；春节月提前 1–4 天 |
| CPI / PPI | 11 天 | 9–15 | 次月 9–11 日 |
| NBS 活动数据 | 15–16 天 | 11–19 | 次月 15 日前后 |
| GDP | 18 天 | 16–21 | 季后 15–18 日 |
| 央行（M0/M1/M2/存贷款/社融） | 12–14 天 | 11–18 | 样本少，标 low 置信 |
| 财政（MOF） | 16–18 天 | 11–25 | 尾部拖到 41 天，需例外清单 |
| 外管局（结售汇/涉外） | 18–19 天 | 15–25 | 次月 15–25 日 |
| 外汇储备 | 7 天 | 7–7 | 最稳 |
| OECD 两指数 | 62–91 天 | — | **受批量入库污染，不可用恒定规则，排除** |

产出：`reports/v2/history/pit/pit_work_step1_lag/`（lag_by_period.csv、lag_stats_by_series.csv、README.md）。

### 3.2 第 2 步：估计可用日期（`scripts/tools/estimate_availability.py`）

- **规则表** `config/estimated_availability_rules_v1.csv`：52 条规则（47 宽表字段 + 海关 5 项），含滞后天数、是否当日可用、置信度、是否纳入、依据；
- **口径**：`estimated_release_date = period_end + lag`；非 PMI 序列自估计发布日**次日 00:00（+08:00）**可用（沿用 B 级保守惯例）；PMI 当月末 **09:30** 可用；
- **估计日期不写入主库**，只存侧车文件 `estimated_available_v1.csv` 供 work 模式读取（主库是 append-only 证据层，派生物走文件，规则更新可随时重建）；
- 初始覆盖 3,373 条 D 记录（WIND 1,958 + SAFE 官方批量 1,415），随批次增长至 5,000+ 条。

### 3.3 第 3 步：work 导出模式

**核心设计决策：PIT_work 做在"面板层"，不做在"记录层"**——记录级 A/B/C/D 证据契约一字不动（项目硬约束"只接受 A/B/C/D，不加 E 等级"），work 是 `export-wide --pit-mode work` 的取值规则：

- `pit.py` 新增 `get_work_snapshot`；`snapshot.py`/`cli.py` 支持 `--pit-mode work` 与 `--estimated-availability` 侧车路径；
- 导出四件套：`*_values.csv`（数值）+ `*_periods`（数据期）+ `*_metadata` + **`*_provenance.csv`（逐格来源标签）**；
- 来源标签四档：**work_A**（官方原值+精确时刻）/ **work_B**（官方原值+发布日期）/ **work_safe_d**（外管局官方批量终值+估计日）/ **work_wind**（Wind 终值+估计日）——下游可按格过滤做敏感性分析；
- 取值语义经过一次重要修正，见 5.1。

## 五、两个重要设计修正

### 5.1 work 模式语义：从"等级优先"到"最新可见期优先"

**问题**：原瀑布"有 A/B 就用 A/B"导致陈旧官方值压制新鲜 Wind 值——CPI 官方证据网眼状分布，2012-06-30 截点曾显示 13 个月前（2011-05）的 CPI=5.5，批次5 补的新鲜数据一格用不上。

**修正**（`pit.py get_work_snapshot`）：每个截点取**可见记录中数据期最新**的；同一数据期既有官方又有 Wind 时**保留官方**。安全边界：provenance 为 work_A/work_B 的格子与严格表一致性仍为 **0 冲突**；Wind 替换陈旧官方值的格子单独记为"升级格"（最终 2,452 格），逐格可查。

### 5.2 浮点噪声修复

用户发现 work CSV 数字"格式不对"。排查：非文本化存储（0 引号字段），实为**二进制浮点噪声**（`0.28090000000000004`）——根因是入库换算用乘法（×0.0001），0.0001 二进制不精确。修复：导出层统一 `round(v,10)`；入库脚本改**除法**（v/10000）；strict+work 重导。已入库记录不重放（append-only），由导出层覆盖。

## 六、GDP 历史修订快照接入

### 6.1 文件语义（经实证确认，关键）

用户提供 Wind 终端 EDB「历史修正」导出两份（`data/raw/wind/修订/`，指标 M0039354）：

- **终值列 = 导出当日的现行值**（两文件均延伸到 2026-Q2），**不是**"修正日期当日可见的序列状态"，不能锚定到修正日期；
- **修正值列非空的行**才记录该修正日期发生的修订事件：值=修正值，生效日=修正日期；
- 20250118 文件：2025-01-18 年度核实修订 7 个季度（2022-Q2~2023-Q4）；20250416 文件：2025-04-16 2025-Q1 发布/修订；
- 两文件终值序列完全一致（0 期差异），与批次9 MCP 终值拉取三方吻合；**初值列与库内 A 级官方原值完全一致**（2022-Q2 初值 0.4 = A 级 0.4），佐证 A 级证据质量。

### 6.2 操作失误与修复（留痕）

1. **失误**：初版脚本误将全部 86 个期间的终值锚定到修正日期，入库 50 行（2014-Q1~2026-Q2），导致 observed 模式在 2025-03-01 可见 2026-Q2 未来值（未来数据泄漏）；
2. **发现**：vintage 链 sanity 检查（`check_gdp_vintage_chain.py`）当场暴露；
3. **修复**（用户明确授权）：一次性 DELETE 50 行（776,150→776,100，日志 `remediation_log.txt`）；按正确语义重新入库 **8 行**（7 个修订季度@2025-01-18 + 2025-Q1@2025-04-16），主库 776,100→776,108。

### 6.3 契约变更（用户批准）

`db.py` 的 D 级"available_at 不得早于 first_seen_at"禁令新增**窄例外**：仅 `release_date_source` 以 `wind_revision_snapshot_` 开头（有据版本日期，非猜测）时放行。新增契约测试 `test_pit_d_available_at_before_first_seen_requires_documented_marker`，6/6 通过。

### 6.4 最终效果

- GDP 获得真实修订 vintage 链：2022-Q2 = 0.4（A 级原值，2022-07-15 发布）→ 0.8（Wind 修订版，2025-01-18 生效）；
- observed 模式三截点验证无未来泄漏：2024-08-01→2024-Q2(A,4.7)；2025-03-01→2024-Q4(A,5.4)；2025-05-01→2025-Q1(A,5.4)；
- strict/loose/work 三表零影响（8 行均落在 A 级覆盖期间）。

## 七、质量保障体系

| 机制 | 说明 |
|---|---|
| 映射逐字核对 | Wind 代码的名称/单位与元数据完全一致才入库；口径不符剔除（M0009973、M0000545 拆分段） |
| 重叠对数 | 每批与库内 A/B 重叠期逐点比对（批次3-8 全部 100% 吻合；批次9 实测出修订偏差，符合预期） |
| 幂等重放 | 内存库二次入库必须全 unchanged |
| strict/loose 排除断言 | D 级任何截点不得进入 strict/loose 快照 |
| 入库前后哈希 | --ingest 断言 strict 快照与 data/exports 文件哈希不变 |
| 手误防线 | 长数值列表用生成器脚本（月末日期自动生成+长度断言+单调性检查），曾兜住 3 次转存手误 |
| 契约测试 | test_work_mode.py（work 语义）+ test_db_contracts.py（含修订快照例外）；当前环境可直接运行正式 pytest 契约 |
| 逐格来源伴随表 | provenance 表让下游能区分每格证据等级，支撑敏感性分析 |

## 十一、经验教训清单

1. **Wind 系列名带"拆分/估计"字样的要逐点甄别**——重叠对数覆盖不到的年份正是估计污染区（M0000545 教训）；
2. **"历史修正"文件的终值列是导出日现行值**，不是快照日状态；只有修正值列非空行记录修订事件；
3. **单位换算永远用除法**（v/10000）不用乘法（v×0.0001），后者引入 1 ulp 浮点噪声；
4. **长数值列表转存用生成器脚本**（日期自动生成+长度断言+单调性检查），手工转存出过 3 次错均被校验兜住；
5. **F 码（如 F3478527）也是官方 EDB 系列**，不是 Wind 加工值；
6. **D 级签名不含时间字段**（项目设计）：值相同的 D 记录幂等去重，版本日期例外需显式标记；
7. **多代码合并拉取省额度**，单次大窗口请求会被截断（≤7 年/窗）；
8. **入库前先查库确认 canonical_series_id**（非制造业 PMI 是 CN_PMI_NONMANUFACTURING 而非猜测的 ID）；
9. **duckdb 查 TIMESTAMPTZ 列需 CAST AS VARCHAR**（py -3.11 环境缺 pytz）；
10. **work 表的正确语义是"最新可见期优先"**，不是"等级优先"——否则会展示 13 个月前的陈旧官方值；
11. **验收应使用正式 pytest 契约**，不要保留与特定批次绑定的手工检查脚本；
12. **任何"让历史数据在过去可见"的操作都必须做未来泄漏 sanity 检查**（修订快照失误就是被这一检查当场抓住的）。
